# Phase 4: Explicit Skill Loading and Agent Discovery

Phase 4 adds the runtime skill-discovery and explicit-loading layer on top of the Phase 3 `SkillCatalog`. The design keeps discovery cheap and descriptor-only, and loads full `SKILL.md` content only when a skill is explicitly selected.
The current design code separates local skill discovery from explicit skill invocation. Its skill loader identifies directories containing `SKILL.md`, exposes compact frontmatter metadata for discovery, and loads the full body at invocation time. The current experimental skill-search area is feature-gated in the inspected implementation snapshot, but it preserves explicit discovery signals such as user input, write pivots, and subagent creation. the implementation also treats skills as a distinct capability rather than folding their bodies into generic plugin metadata.

TermAgent adapts those concepts to the existing Node + ANSI/VT + ARMv7/Termux runtime without importing the existing UI model or heavyweight dependency stack.

## Runtime flow

```text
user prompt
   |
   v
SkillCatalog
   |
   v
search_skills
   |
   +--> compact SkillDescriptor results
   |
   v
model selects exact skill
   |
   v
use_skill
   |
   +--> live catalog lookup
   +--> realpath/root containment
   +--> SHA-256 verification
   +--> full SKILL.md body
```

The full body is never included in the normal automatic discovery listing. The `use_skill` output is preserved in the active conversation instead of being reduced by the generic tool-output summarizer.

## `search_skills`

The shared search tool accepts a query and optional result limits/thresholds. Matching is deterministic and uses the descriptor fields only: skill ID, name, and description. Exact IDs/names receive the strongest scores, token coverage is weighted, and a small synonym map improves common developer queries such as `pr`/`pull request`, `bug`/`debug`, `tests`/`verification`, and `database`/`db`/`sql`/`migration`.

Results below the minimum relevance threshold are dropped. A result also has to stay within a bounded delta of the best match, preventing an unrelated descriptor from appearing merely because the result set is small. Ties are resolved by skill ID for deterministic output.

## `use_skill`

`use_skill` accepts one exact skill ID. The loader:

1. reads the live Phase 3 catalog;
2. rejects unknown skills and model-disabled skills;
3. optionally rejects `user-invocable: false` skills for direct user invocation;
4. resolves the skill and its root through `realpath`;
5. requires a regular `SKILL.md` file inside the configured root;
6. recomputes the SHA-256 digest and compares it with the catalog descriptor;
7. only then returns the full skill body.

This closes the stale-index gap where a skill can change between discovery and invocation.

## Automatic rediscovery signals

The agent performs an initial `user_input` discovery for each normal turn. Additional discovery can happen after meaningful context pivots:

- `write_pivot`: a successful file-write/edit operation supplies the written paths rather than replaying the entire original prompt, keeping the query focused on the new artifact.
- `subagent_spawn`: background/parallel agent creation triggers another descriptor search for the delegated context.
- `explicit`: supported by the shared discovery API for direct/manual search requests.

Each distinct signal/query pair is processed once per agent run. Explicit `/skill` invocation sets `skillDiscoverySuppressed` so the loaded skill body is not fed back into automatic discovery.

## Explicit `/skill`

The CLI accepts:

```text
/skill <skill-id> [task arguments]
```

The command uses the same live loader and `requireUserInvocable` guard as the tool path. Namespaced plugin skills use the IDs generated by Phase 3, for example `<plugin>@<marketplace>:<skill>`. A successful direct invocation records `skill.load` with source `slash`; a rejected invocation records `skill.skip`.

## Session events

Phase 4 adds three session event types:

```text
skill.search
skill.load
skill.skip
```

Search events record the signal, query, result count, and compact relevance scores. Load events record the skill ID and digest. Skip events record a stable reason such as `no-match`, a digest failure, or an invocation policy rejection.

## Loop safety

Skills use the existing agent tool-loop guard rather than introducing a second loop system. Repeated identical `use_skill` calls are therefore subject to the same repeat and semantic no-progress limits as other tool calls. Discovery is also query-keyed per turn, so identical automatic searches are not reissued indefinitely.

## Scope boundary

Phase 4 intentionally does not add remote skill registries, plugin component activation, plugin manager UI, trust/revocation UI, dependency resolution, or context-budget optimization. Those remain separate later phases.

## Verification

The Phase 4 gate covers:

- thresholded and deterministic relevance ranking;
- descriptor-only search results with no skill body leakage;
- exact loading with digest verification;
- invocation policy checks;
- initial discovery and write/subagent rediscovery;
- explicit `/skill` invocation and suppression of recursive discovery;
- session search/load/skip events;
- repeated skill-loading loop protection;
- clean build, focused tests, complete suite, source hygiene, package dry-run, and extracted-package smoke verification.
